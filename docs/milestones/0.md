## 1. How others solved this

### Copying a vendored build and its tests, with provenance kept
| What others do | Label |
|---|---|
| Chromium: every third-party folder has a `README.chromium` giving the upstream URL and revision and how it is updated. [docs](https://chromium.googlesource.com/chromium/src/+/main/docs/adding_to_third_party.md) | Verified |
| Mozilla: a `moz.yaml` per vendored library records the origin, the commit, and any local patches. [docs](https://firefox-source-docs.mozilla.org/mozbuild/vendor/index.html) | Verified |
| Go and Rust: a generated list (`vendor/modules.txt`, `.cargo-checksum.json`) that the tool checks, so a vendored file can't change by accident. [Go](https://go.dev/ref/mod), [Cargo](https://doc.rust-lang.org/cargo/reference/source-replacement.html) | Verified |
| GitHub's own action template commits its built output and has a workflow that rebuilds it and fails on any difference ("check-dist"). [workflow](https://github.com/actions/typescript-action/blob/main/.github/workflows/check-dist.yml) | Verified |
| Reproducible Builds: same source, same environment, same instructions give bit-identical output. [definition](https://reproducible-builds.org/docs/definition/) | Verified |
| LGPL 2.1 (JSBSim's licence): ship the licence text and give equal access to the exact source and build recipe. [FAQ](https://www.gnu.org/licenses/gpl-faq.html), [FFmpeg's checklist](https://www.ffmpeg.org/legal.html) | Verified |
| FDM: a clean rebuild in another folder, on the same machine, gave the same four files byte for byte. Its `build-info.json` records a hash of the binaries and of the C++ host sources. | Supported |

**Choice.** One folder, `jsbsim/`, holds FDM's build and its tests in FDM's own layout, so FDM's scripts run there almost unchanged. Three things keep the copy honest:
1. `jsbsim/README.md` says where everything came from (repo, path, commit) and lists every local change, as Chromium and Mozilla do.
2. `provenance.json` lists each copied file with the hash of its original. A test fails if a copied file changes without its entry being updated in the same pull request (Go's and Cargo's method).
3. A rebuild workflow in GitHub Actions rebuilds the WebAssembly and fails on any byte of difference (GitHub's check-dist method).

### Emscripten output in a module Worker, in a PWA with no bundler
| What others do | Label |
|---|---|
| MDN: `new Worker(new URL('./worker.js', import.meta.url), { type: 'module' })`; the Worker then uses ordinary `import`. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Worker/Worker) | Verified |
| Safari has had module Workers since Safari 15. [WebKit](https://webkit.org/blog/11989/new-webkit-features-in-safari-15/) | Verified |
| Emscripten's `.mjs` output has one default export, an async factory. It finds its `.wasm` next to itself and compiles it while it downloads, which needs the server to label it `application/wasm`; otherwise it falls back to a slower path. [docs](https://emscripten.org/docs/compiling/Modularized-Output.html), [source](https://github.com/emscripten-core/emscripten/blob/main/src/preamble.js) | Verified |
| GitHub Pages labels `.wasm` as `application/wasm` and `.mjs` as JavaScript. Read from FDM's live page while planning. | Verified (the live site) |
| Pyodide requires a module Worker for its `.mjs` build; SQLite's ES-module build avoids the classic Worker's "where am I loaded from" problem. [Pyodide](https://pyodide.org/en/stable/usage/webworker.html), [SQLite](https://sqlite.org/wasm/doc/trunk/gotchas.md) | Verified |
| FlightDynamicsLab and WebFlight run JSBSim in a dedicated Worker and pass state by message, because GitHub Pages can't enable shared memory. [FDL](https://github.com/tkir97/FlightDynamicsLab), [WebFlight](https://github.com/rtnicolae/WebFlight) | Verified |
| FDM's test page ran a module Worker that imported the Emscripten file by its address. On the owner's iPhone (Safari 27.2, in a Safari tab): 7.7 µs per step in the Worker. | Verified (his phone) |
| **Found while planning:** FDM's page also posted the `.wasm` bytes to the Worker, but FDM's Emscripten files never read them (`instantiateAsync(void 0, …)` in both `.mjs` files). The Worker fetched the `.wasm` itself. So that is the path the phone proved. | Verified (the committed files) |
| Three things FDM's phone run did not have: a Worker made of several unbundled files (FDM's was one bundled file), a service worker in front of it, and the installed home-screen app. | Reasoned; settled by PR 6's Chromium run and the phone check |

**Choice.** FDM's proven path, unbundled. A module Worker imports the Emscripten file by address, and that file fetches its own `.wasm` from beside it. The page posts only the data files. The Worker's message protocol is FDM's, unchanged.

### Caching `.wasm` and data files in a service worker
| What others do | Label |
|---|---|
| MDN: cache the app's files in the `install` event under a versioned cache name; delete old versions in `activate`. [MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Caching) | Verified |
| Workbox's update recipe: the new worker waits; the page offers the update; a tap posts "skip waiting"; the page reloads when the new worker takes control. [Chrome docs](https://developer.chrome.com/docs/workbox/handling-service-worker-updates) | Verified |
| WebKit: a home-screen web app keeps its storage (no 7-day clear-out), with the same generous quota as Safari. [storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [7-day rule](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/) | Verified |
| Wings' `sw.js` (after Rage's): exactly that pattern, with `cache: 'reload'` so GitHub's 10-minute HTTP cache can't hand a new version a stale file, and deleting only caches with its own prefix. Its update offer works on the owner's iPhone. | Verified (his phone) |
| Requests made from inside a Worker go through the page's service worker in Chrome and Firefox. WebKit's bug tracker shows Safari doing it too, but no WebKit page says so for module Workers. [bug 252664](https://bugs.webkit.org/show_bug.cgi?id=252664) | Reasoned; settled by the Airplane Mode check on the phone |

**Choice.** Wings' `sw.js`, with `fsg-` in place of `wings-`. Its file list gains the Worker's modules, both Emscripten files, both `.wasm` files and the seven data files. Wings' test that the list matches what the app loads is extended to follow the Worker and to require each `.wasm` beside its `.mjs`.

### How TypeScript becomes plain JavaScript, and how the copy stays checked
- `tools/from-fdm.mjs` does the whole copy from a checkout of FDM at `e478825`. Nothing is converted by hand. For a `.ts` file it:
  1. blanks the types with Node's own stripper;
  2. keeps any line that was nothing but types as a `//` comment, so the descriptions of the Worker's messages and the options stay readable where they were;
  3. renames `.ts` to `.js` in import lines and applies the listed folder changes;
  4. adds the "came from" header.
- After that the `.js` files are FSG's source. There is no TypeScript, compiler or bundler in the repo.
- `provenance.json` records for each copied file: the FDM or Wings path, the commit, the original's SHA-256, the copy's SHA-256, and how it was made ("byte for byte", "types removed", or "changed: why"). JSBSim's 485 data files are covered instead, as whole folders, by upstream's own git tree ids in `pins.env`, which is the stronger check.
- `tests/provenance.test.js` runs in GitHub Actions on every push. It fails if a copied file no longer matches its entry. Changing a copied file on purpose (milestone 1 will) means updating its entry in the same pull request, so every change since the copy is on record.
- `node tools/from-fdm.mjs --check <FDM checkout>` re-derives every file from the originals and compares. It is run in the session for each copy pull request, and its output goes in the pull request.
- The real proof that removing types changed nothing: every copied test passes in both builds (PR 5).

### Where the "came from" note goes
`CLAUDE.md` asks for a comment at the top of each copied file. Files that are adapted or converted get it: all the `.js`, `sw.js`, `index.html`, `style.css`, the workflows, `check-data.sh`. Files that must stay byte-identical can't carry one without breaking the check that proves they are FDM's: the binaries, JSBSim's data, the C++ host and build files (their hash is in `build-info.json`), the build scripts, the fixtures and NASA data, the icons. For those, `jsbsim/README.md`, `provenance.json` and the commit message say where they came from. **This is my reading of the rule; approving the plan approves it.**

### How JSBSim reaches the Worker in the app
1. `src/sim/c172x-files.js` lists the seven files: `aircraft/c172x/c172x.xml`, `c172ap.xml`, `reset01.xml`; `engine/eng_io320.xml`, `prop_75in2f.xml`; `systems/GNCUtilities.xml`, `Autopilot.xml`.
2. `src/fdm.js` (page side) starts the module Worker `src/sim/worker.js`, fetches the seven files from `./jsbsim/jsbsim-data/…`, and posts them in FDM's `init` message with the address of `./jsbsim/dist-wasm/fdm-weh.mjs`.
3. The Worker imports that file, which fetches `fdm-weh.wasm` from beside it. The Worker writes the seven files into JSBSim's in-memory file system and loads `c172x`.
4. The service worker has every one of these cached, so it all works offline.
5. **Fallback.** If the fast build doesn't start, `src/fdm.js` starts a fresh Worker with `fdm-jseh`. It also leaves a marker before starting the fast build and clears it afterwards, so if the whole app dies during start-up, the next launch goes straight to the fallback. FDM kept its marker in session storage, which a home-screen app loses when it is relaunched, so FSG keeps it in local storage as `fsg.fdmStarting`.

## 7. A look ahead: proposals for milestones 1 to 4

Proposals only; each milestone gets its own plan.

1. **Milestone 1, the Worker's clock.** FDM's Worker steps when the page sends it a "tick", and catches up by elapsed time, so the physics already keeps real time at 30 frames a second. `CLAUDE.md` wants the Worker to run its own 120-a-second clock, and timers inside a Worker on iOS are not exact. I'd propose milestone 1 measures both on the phone before choosing. That adds one phone check to a milestone described as headless: "with Low Power Mode on, the overlay shows 120 steps a second held."
2. **Milestone 1, "matching native".** A flown circuit is closed-loop, and FDM showed that anything closed-loop turns a last-digit difference into a visible one. I'd propose the checkride flies the circuit in WebAssembly, records the controls step by step, replays them through native, and compares with FDM's noise-relative lines, not fixed small numbers.
3. **Milestone 2** brings Three.js and the first real screen. I'd propose asking then for one test-only tool, Playwright, so the Chromium run joins GitHub Actions and no longer runs only in the session.
4. **Milestone 3** is the largest by far. I'd propose planning it as two: the F-4C's aircraft file against the NASA data and the flight manual, headless; then its stability augmentation, the model, the plumes and the feel on the phone.
5. **Milestone 4, the tiles.** Hawaii is about 175 MB in Wings' repo, and GitHub advises keeping a repo and a Pages site under 1 GB. Copying them is within that. One thing to decide in that plan: whether the phone downloads them again for FSG or FSG reuses what Wings already put on the phone.

## Lines that failed first, and what was found

**1. The rebuild on GitHub's machine (PR 4), first run.** Both `.wasm` files came out longer than the committed ones: 1,734,967 bytes against 1,734,938, and 2,236,952 against 2,236,922. The two `.mjs` files and every compiler flag matched.
- Cause: JSBSim's own build file (`src/CMakeLists.txt`, upstream, unmodified) adds " [GitHub build N/commit …]" to its version text when it finds `GITHUB_RUN_NUMBER` set. Verified (upstream's source; the text inside both binaries).
- Check: rebuilt in the session with GitHub's two values set by hand, the result was GitHub's files exactly (`6c9781cd…`, `f0347a55…`). So the stamp was the whole difference. Verified (against GitHub's machine).
- What was done, with the owner's agreement: the rebuild workflow, and the native-build script, build without that one variable. The committed binaries, FDM's build scripts and the tests were not changed. The second run matched 4 of 4.
- What it also showed: the same inputs give the same bytes on two different machines. That was the open risk in the plan ("byte-identical rebuilds are not promised across machines"). Verified for these two machines.

**2. The external-forces test in GitHub Actions (PR 5), first run.** 74 of 75 passed; the forces test could not open a generated test aircraft, `c172x_ext20`.
